### 2.2 缺陷清单

**缺陷 1 · 错误码不规范，且泄露内部路径**

- 抛出的是 `FileNotFoundException` 原文，不是契约错误码 `MODEL_UNAVAILABLE`。
- `MODEL_UNAVAILABLE` 在代码中仅于实验模式 `PlanMode.REMOTE` 时抛出（`MainActivity.kt:286`），LOCAL 缺模型走不到该分支。
- 状态栏直接展示 `/data/user/0/com.example.interviewfeedback/...` 私有路径，不适合出现在用户界面。

**缺陷 2 · 失败零事件记录**

实测 App 私有目录内容：

```
files/ = experiments, hw_cached_resid.list, tasks
files/tasks/ = 空
files/events.jsonl = 不存在
```

原因：报错发生在 `engine.begin()`（`MainActivity.kt:293`）之前，`TaskCoordinator` 尚未创建，任务未 generate，`JsonlEventSink`（`:165`）没有任何 `TaskEvent` 可写。

后果：该场景**无法按清单要求导出可归档的原始证据**，只能用屏截图作为旁证。

### 2.6.2 结果解读（这部分不能当作算法评价）

**输入内容与参考要点主题不一致。** S01 这段录音通篇讲的是「防诈骗宣传」（骗局、验证码、转账核实身份），而 App 当前的参考要点是「调查居民需求 / 组织分层宣传 / 评估宣传效果」。题目本身对不上，因此 0/3 只能证明链路通，不能说明覆盖算法判错。

**但有一处值得记下来的现象。** 转写中出现了「按老年人和年轻人**分别**讲解真实案例」，这在语义上就是「组织分层宣传」的核心表述，相似度却只有 **0.439**，距 0.54 有明显差距。若后续用对口内容复测仍出现同类情况，说明阈值 0.54 对「无字面重合的意译表述」偏严，风险方向是**假阴性**（漏判），而非此前担心的假阳性。

**疑似缺陷：依据引用重复。** 三条要点的「依据」几乎都指向同一句「人分别讲解真实案例」，「调查居民需求」引的则是「请社区工作人员按老年人和年轻人分别讲解真实案例」。同一语义片段被复用为三条不同要点的依据，需确认是取 top-1 句子的实现所致，还是匹配逻辑存在重复命中。

## 2.8 分析中闪退（native 内存压力）

### 2.8.1 证据链

**一、任务在 M2 阶段被打断。** `tasks/5eb25607-….json` 中 `measurements` 仅含 M0、M1 两条，`total_elapsed_ms`、`feedback_elapsed_ms`、`feedback` 全为 `null`，`status` 为 `INTERRUPTED`。M2（ASR）从未返回。

**二、无应用层异常。** logcat 共 12,957 行，覆盖 11-09 至 11-14 20:47，其中 `FATAL EXCEPTION`、`AndroidRuntime`、`Fatal signal`、`signal 11`、`lmkd`、`lowmemorykiller`、`ANR in`、`tombstone` **全部 0 命中**；`dumpsys dropbox --print` 62,986 B 中该包名 **0 命中**。说明没有产生 Java 崩溃栈，也不是 ANR。

**三、内存是嫌疑主因。** `dumpsys meminfo com.example.interviewfeedback` 实测：

| 项 | 值 |
|---|---|
| Native Heap Alloc | **4,240,611 KB（约 4.04 GB）** |
| Native Heap Size | 4,457,208 KB（约 4.25 GB） |
| Native Heap Free | 210,564 KB |
| Native Heap Rss | 21,184 KB |
| Dalvik Heap Alloc | 3,917 KB |
| `dalvik.vm.heapsize` | 512 MB |

**四、`INTERRUPTED` 是重启后补写的。** 与 JVM 用例 `restartMarksInterruptedWithoutResubmission` 的语义一致：`TaskCoordinator` 在下次启动时把未终结的任务标记为 `INTERRUPTED`，并不重新提交。

### 2.8.2 成因判断（已因新证据修正）

**初判**：任务 4 在 M2（ASR）阶段 native 内存达到约 4 GB，被系统以内存压力杀掉，进程随后重启，遗留任务被补记为 `INTERRUPTED`。

**修正依据（2026-11-14 20:51 实测）**：随后一次录音 **46.34 秒**（741,376 samples，**比任务 4 的 44.54 秒更长**）在 M2 阶段仅耗时 16,871 ms 便正常完成，覆盖 3/3，**未崩溃**。因此：

1. **音频时长不是崩溃的充分条件** —— 更长的音频可以成功。
2. **M2 耗时波动极大**：27.90 s 音频 → 11,461 ms；37.76 s → 27,538 ms；46.34 s → 16,871 ms。耗时与音频长度不呈线性关系，说明内部另有变量（切句数量、VAD 分段数、文本长度等）。
3. **native 约 4.24 GB 是常态分配**：崩溃后的快照（Alloc 4,240,611 KB）与成功后的快照（Alloc 4,243,421 KB）几乎相同。该量级本身不导致崩溃，只是基线。

**当前可确认的只有**：任务 4 在 M2 阶段异常终止、进程重启、无 Java 崩溃栈、无 ANR。**触发原因尚不明确**，不能归因为「音频长度超过某阈值」。

**仍然成立的两点**：这不是用户取消，也不是应用层异常。

### 2.8.3 影响

- **存在偶发的分析中断**：已观测 1 次（44.54 秒），随后 46.34 秒同路径成功，属**间歇性**而非必然。
- 中断时不留下任何可读信息：`error_code` 为空、UI 无提示、无事件记录，**用户无法得知发生了什么**，只能感知「App 退出了」。
- 威胁「连续录音」与「60 秒上限」两项验收内容。
- Native Heap Alloc 约 4.24 GB 而 Rss 差别极大（崩溃后 21 MB / 成功后 636 MB），说明大量内存被换页压缩，设备在内存压力下的回收行为直接影响可用性。

### 2.8.4 待验证

1. **是否稳定复现**：已尝试一次 46.34 秒（未复现），需继续积累同长度样本。
2. **触发条件**：对比任务 4 与其余任务在切句数量、文本长度、VAD 分段数上的差异。
3. **内存峰值出现在哪个模块**：在分析过程中周期性采样 `dumpsys meminfo`，而不是只在事后取一次快照。
4. **与常驻模型权重的关系**：导入模型后常驻的 1.67 GB 权重是否已映射进进程地址空间。

## 2.11 重新连接手机时的 USB 枚举失败（设备侧阻断，2026-11-15）

B1-01 需要重新连机。本次重新插线后 adb 一度完全找不到设备，现记录整个过程与判据，避免后续把「电脑看不见手机」误判成 App 或代码问题。

**时间线**

| 阶段 | 现象 | 证据 |
|---|---|---|
| 首次检测 | `adb devices` 空；`settings get global airplane_mode_on` 无法读取 | `_air_chk.txt` |
| 重启 adb server | 仍为空 | `_air_chk2.txt` |
| 设备树检查 | 出现 `Unknown USB Device (Device Descriptor Request Failed)`，`Problem = CM_PROB_FAILED_POST_START`，`InstanceId = USB\VID_0000&PID_0002\5&96C427&0&12` | `_usb_enum.txt` |
| 用户提供系统弹窗截图 | Windows 报「无法识别的 USB 设备 / 跟这台计算机连接的前一个 USB 设备工作不正常」 | 用户在对话中提供 |
| 强制重新枚举 | `pnputil /disable-device` 与 `/enable-device` 均报 `The device is not connected`；`pnputil /scan-devices` 报 `Access is denied`（需管理员） | `_usb_reenum.txt`、`_usb_scan.txt` |
| 换线后 | 手机被正确枚举：`USB\VID_339B&PID_107D\AQULVB4522044827`，识别为 `HONOR 200`（WPD 类），并有 `USB Mass Storage Device` | `_usb_try3.txt`、`_usb_try4.txt` |
| 最后一次检测 | 手机再次从设备树消失，`adb` 仍空 | `_usb_try5.txt`、`_usb_poll2.txt` |

**判据**

`VID_0000&PID_0002` 不是手机的真实识别码，它是 Windows 在**设备描述符请求失败**时填的占位值。含义是 USB 枚举在最底层就没握手成功，设备还没能报出自己是谁。这与以下情况是两回事：

- **不是**「USB 调试没开」：那个开关的效应是「枚举成功但没有 ADB 接口」，设备树会正常显示型号；
- **不是**「授权弹窗没点」：授权发生在 ADB 接口存在之后；
- **不是** adb 版本或服务问题：adb server 已重启两次，`kill-server` / `start-server` 均正常返回。

换线之后设备能被认成 `HONOR 200`，说明这台电脑的 USB 口、驱动和 adb 环境都是好的。剩下没有 ADB 接口，指向 USB 调试开关或该线的数据针脚。

**结论**

这次停滞属于**设备侧环境阻断**，与 §2.9 已通过的 4 项验收记录无关——那 4 项是在上一轮连接正常时采集的，证据链完整，不受本次断连影响。B1-01 需等 USB 链路恢复（换线或打开 USB 调试）后再做。

## 2.12 否定作用域修复（S25 k4 误判闭环，2026-11-15）

§2.10 发现 S25 k4 得 0.8941 被判「已覆盖」，而转写是「不再收集反馈和提供帮助渠道」。本节记录根因定位、修法与实测结果。

**根因不在正则，在切句。**

`answer_clauses()` 对超 28 字且不含否定的 clause 做 14 步滑窗，切出 5 句。其中：

- `s2` = 完整原句（含「不再」）
- `s5` = **`收集反馈和提供帮助渠道`**——滑窗从第 28 字开始截，**把「不再」切掉了**

### 5.4 异常协议九项（S3-T3）

| # | 用例 | 期望 | 实测 | 结果 |
|---|---|---|---|---|
| 1 | 版本号不符 | 409 `VERSION_MISMATCH` | 一致 | 通过 |
| 2 | 载荷结构错误 | 400 `INVALID_PAYLOAD` | 一致 | 通过 |
| 3 | 请求体 5 MiB 超限 | 413 `PAYLOAD_TOO_LARGE` | 一致 | 通过 |
| 4 | 错误凭据 | 401 `UNAUTHORIZED` | 一致 | 通过 |
| 5 | 未知模块 `M9` | 404 `UNKNOWN_MODULE` | 一致 | 通过 |
| 6 | `remaining_budget_ms=1` | 504 `DEADLINE_EXCEEDED` | 一致 | 通过 |
| 7 | 同键重发 | 200 两次，输出一致 | 一致，第二次命中缓存 | 通过 |
| 8 | 同键异内容 | 409 `REQUEST_CONFLICT` | 一致 | 通过 |
| 9 | 并发同键 | 一个 200、一个 409 `IN_PROGRESS` | `a:200` / `b:409` | 通过 |

两处记录在案的边界行为：

1. **缓存重放时 `elapsed_ms` 不归零**：网关直接回放已缓存的响应体，第二次返回的 `elapsed_ms` 沿用首次值。客户端不能用它判断本次耗时，应以网络往返为准。
2. **401 / 404 在读完请求体前返回**：客户端仍发送较大 body 会触发 `ConnectionReset`（WinError 10054），读不到响应体。用小 body（`pcm_b64="AAAA"`、`sample_count=1`）可正常读到 `error.code`。

### 5.6 本轮发现并修复的契约缺陷

| 提交 | 内容 | 影响 |
|---|---|---|
| `5dc1da0` | `contracts/module-result.schema.json` 的 `M3Output.keypoints` 补 `text` 字段（`minLength: 1`）并加入 `required`，共 +5 行 | 修复前 REMOTE 全链路在 M3 稳定 500，`elapsed_ms` 仅 31–78 ms |
| `67f6c2c` | `server/gateway/protocol.py` 新增 `leaf_errors()` / `describe()`，`check_schema` 改调 `describe()`，+20 −2 | 报错从 `Invalid fields at $` 落到 `Invalid fields at payload.keypoints.0: 'text' is a required property` |

根因：`module-result.schema.json` 的 `M3Output.keypoints` 只允许 `keypoint_id` + `vector` 且 `additionalProperties: false`，而 `module-request.schema.json` 中作为 M4 输入的同名结构**要求**必须带 `text`。两份契约互相矛盾，M3 输出永远接不上 M4。

S2 未暴露该问题的原因是 `run_sample_batch.py` 直接调用模块函数、不经过网关的 `check_output`，只有走真实 HTTP 才会触发。

回归结果：`server/tests/test_gateway.py` 修复前后均 5/5 通过；连同 `test_measurement_contract` + `test_real_contracts` 合计 **8/8，3.556 s**。

### 5.10 本节与 B1 的关系

S3 是**执行位置**维度的验证，B1 是**功能场景**维度的验证，两者不互相替代：

- B1 六类场景证明「单机上功能正确」，全程 LOCAL。
- S3 证明「同一份输入换执行位置后结果不变」，覆盖 REMOTE 与混合两种部署形态。

B1 的结论不受 S3 影响；S3 的结论也**不能**被用来声称「两机验收完成」。
