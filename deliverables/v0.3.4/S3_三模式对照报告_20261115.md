| 5 | 未知模块 | 路径改为 `/modules/M9/execute` | 404 `UNKNOWN_MODULE` | 404 `UNKNOWN_MODULE` | 通过 |
| 6 | 执行超时 | `remaining_budget_ms=1` | 504 `DEADLINE_EXCEEDED` | 504 `DEADLINE_EXCEEDED` | 通过 |
| 7 | 同键重发 | 同一 `(task_id, attempt, plan_version, module_id)` 连发两次 | 200 / 200，输出一致 | 200 / 200，`output` 完全一致，第二次 0 ms | 通过 |
| 8 | 同键异内容 | 同键换 `payload` | 409 `REQUEST_CONFLICT` | 409 `REQUEST_CONFLICT` | 通过 |
| 9 | 并发同键 | 同键两个 M2 请求，间隔 0.4 s | 先到 200，后到 409 `IN_PROGRESS` | `a: 200`，`b: 409 IN_PROGRESS` | 通过 |

补充观察（实现行为，非缺陷）：

- **缓存命中返回原结果体**：第 7 项第二次请求 `elapsed_ms` 沿用首次值，不归零。因为网关直接回放已缓存的完整结果体，而非重新计时。客户端若以 `elapsed_ms` 判断是否走缓存会误判，应以网络往返时间（0 ms）为准。
- **提前拒绝会重置连接**：401 / 404 在读取请求体之前返回，若客户端仍在发送大 body，服务器关闭连接会导致客户端 `ConnectionReset`，读不到响应体。用小于 4 KiB 的 body 复测即可正常拿到 `error.code`。属于 HTTP 提前拒绝的正常表现，调用方应容忍。

### 5.3 重传核算

三样本 × 三模式共 18 次远程调用（REMOTE 12 次 + MANUAL_MIXED 6 次），**未出现超时重试、未出现重复投递**，重传次数 0。链路上不存在需要重传的场景，因此本批字节数等于有效载荷字节数。

连续远程节点（REMOTE 模式）的回传链路为：

`M1 输出(712,069) → 作为 M2 输入(712,047) → M2 输出 transcript(799) → 作为 M3 输入的一部分(1,052) → M3 输出向量(81,741) → 作为 M4 输入(81,720) → M4 输出 matches(951)`

## 6. 本轮发现并修复的契约缺陷

**现象**：REMOTE 模式在 M3 环节稳定返回 HTTP 500 `INTERNAL_ERROR / "Module failed"`，`elapsed_ms` 仅 31–78 ms；LOCAL 模式同一 payload 完全正常。

**定位链路**：

1. 网关 `execute()` 中 `check_output(body, data, dimension)` 抛出 `ProtocolError("INVALID_PAYLOAD", "Invalid fields at $")`，被包成 `RuntimeError("Invalid adapter result")`，再由外层 `except Exception` 转成 500。
2. 错误位置显示为 `$`（根），因为顶层 schema 是 `oneOf`（OK 分支 + ERROR 分支），任一分支失败都报在根。
3. 展开子错误后定位到真实原因：

```
SUB path: ['output','embeddings','keypoints',0] validator: additionalProperties
msg: Additional properties are not allowed ('text' was unexpected)
```

**根因**：`contracts/module-result.schema.json` 中 `M3Output.keypoints` 只允许 `keypoint_id` 与 `vector`，且 `additionalProperties: false`；而 `server/modules/semantic.py` 的输出实际带 `text`。更严重的是，`contracts/module-request.schema.json` 中作为 M4 输入的 `M3Output` **要求** `keypoints` 必须含 `text`——两个契约互相矛盾，导致 M3 的输出永远无法通过校验后进入 M4，REMOTE 模式整条链路不可用。

**修复**：在 `module-result.schema.json` 的 `M3Output.keypoints` 中补 `text`（`minLength: 1`），并把 `text` 加入 `required`，与请求侧保持一致。

**回归**：`server/tests/test_gateway.py` 修复前后均 5/5 通过；修复后 REMOTE / MANUAL_MIXED 三样本全部实跑成功。

**为什么 S2 没暴露**：S2 的批跑脚本 `run_sample_batch.py` 直接调用模块函数，不经过网关的 `check_output`，所以该缺陷在桌面批跑中不可见，只在真实的 HTTP 远程执行路径上触发。

### 6.1 配套改进：校验报错落到具体字段

定位这个缺陷的最大成本不在修改，而在报错信息。原实现 `check_schema` 只取顶层第一个错误，而 `module-result.schema.json` 顶层是 `oneOf`（OK 分支 + ERROR 分支），任一分支失败都报在根路径 `$`，真实字段被藏在子错误里。

已改为展开 `error.context` 取路径最深的一条叶子错误，输出形如：

```
Invalid fields at output.embeddings.keypoints.0: 'text' is a required property
```

根级错误仍报 `$`，行为向后兼容。真实网关实测：

| 请求 | 结果 |
| --- | --- |
| M3 请求 `keypoints[0]` 缺 `text` | 400，`Invalid fields at payload.keypoints.0: 'text' is a required property` |

## 9. 下一步建议

1. **接第二台手机**：接入后在同一台电脑的网关上各跑一次 REMOTE，补齐 S3-T1 的「两机」维度；这是唯一还卡在设备数量上的验收项。
